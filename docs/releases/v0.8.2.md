# v0.8.2 — Explicit TTY control and durable host-terminal integration

## Added

- **`dworm exec -t/--tty`** explicitly allocates a PTY in the container, and
  **`-T/--no-tty`** disables it. Automatic PTY allocation when stdin and stdout
  are both terminals remains the default. Pipes retain separate, unmodified
  stdout/stderr and the command's exit code. The flags are mutually exclusive
  and also control plain `docker exec` with `--no-bridge`.
- **Container-side TERM fallback** for `shell` and bridge TTY `exec`: pass the
  host TERM through when its terminfo is available in the container; otherwise
  prefer `xterm-256color`, `xterm`, then `vt100`. With no installed terminfo,
  default to `xterm-256color`. This handles host tmux's `tmux-256color` in minimal
  devcontainer images.

## Fixed

- **Permanent interactive-shell loss exits 255** with a one-line stderr message
  after restoring the host terminal. An instance stop or lost event connection
  ends the shell promptly; reconnection has an independent two-minute deadline.
  Previously shutdown races could return success, other loss paths exited 1,
  and the shell reconnect wait had no independent deadline.
- Terminal signal handlers are installed before entering raw mode, and the TUI
  stops layout updates before restoring the terminal. Ctrl-C/Ctrl-Z/Ctrl-\\ stay
  container input bytes. Initial size and SIGWINCH changes propagate to the
  container PTY, including when another device takes over a host tmux session.
- Exec-socket startup handshakes have a ten-second deadline; running commands
  have no execution deadline. Shell start failures now preserve 126/127 too.

## Terminal lifetime and exit codes

`tmux -L massimo new-session -d -s term-ID -- dworm shell` and
`... -- dworm exec -t -- codex` work with cwd set to the project directory.
Detaching a tmux client leaves the container process running because tmux keeps
dworm's host PTY open. PTY output merges stdout and stderr and uses terminal
processing; use `-T` for clean machine-readable stdio.

- Normal shell/exec exits return the container process's status (signals: 128+n).
- A started exec lost with the bridge/socket exits **255**, with a stderr
  diagnostic, and is never rerun. Its outcome is unknown.
- Interactive `shell` still starts a **new shell** after a successful bridge
  reconnect. It exits **255** when the instance stops or recovery fails.
- **125** remains an exec failure before starting; **126/127** mean the command
  could not be executed or found.

The original shell/exec does not survive bridge loss: the endpoint hangs up
the TTY session, then escalates to TERM/KILL. A container stop also destroys its
processes. Host tmux preserves the host terminal, not the container processes.

## Verification

PTY-driven tests run real host clients through an instance socket and a real
endpoint over an in-memory bridge. They cover raw-mode restoration on normal
exit, rejection, signals, bridge loss and instance stop; initial size and resize
propagation; control-key bytes; and exit-status forwarding. No Docker is needed.

## Upgrading

Install the new host and run `dworm stop` in each workspace with an older running
instance, then start it again. The bridge protocol is unchanged.
