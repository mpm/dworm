# v0.5.0 — Project environments and refreshable host commands

## Highlights

Configure project-specific environment variables and generate short-lived tokens
on the host before starting a devcontainer. Periodic refreshes are shared across
the initial shell, separate `dworm shell` sessions, and `dworm exec` commands.

## Added

- Optional `.dworm.config` in the workspace root, with a `bind` default and a
  `host_env.command` argument array.
- Optional `.dworm.env` for static dotenv assignments.
- Host-command execution before container startup, with a configurable timeout
  and optional `refresh_interval` such as `1h`.
- Environment precedence: CLI overrides, host-command output, `.dworm.env`, then
  the inherited container environment. Explicit `--bind` overrides configuration.
- Atomic, private environment snapshots shared by all dworm launch paths.
- Prompt-time refresh in interactive Bash sessions, preserving user initialization
  and prompt hooks. Session-specific CLI overrides stay pinned.
- Replacement semantics for successful refreshes: omitted variables fall back to
  lower-priority values. Failed refreshes retain the last successful snapshot.
- Unit, protocol, Bash-session, and Docker integration coverage for environment
  loading, refresh, precedence, removal, and failure handling.

## Example

`.dworm.config`:

```toml
bind = "127.0.0.1"

[host_env]
command = ["bash", "./scripts/github-token.sh"]
refresh_interval = "1h"
timeout = "30s"
```

The command runs on the host with the workspace as its working directory and
prints assignments such as `GH_TOKEN=...` to stdout. Diagnostics go to stderr.
Omit `refresh_interval` to run only at startup.

See the [README configuration guide](../../README.md#project-environment-and-host-startup-commands)
for dotenv syntax and complete lifecycle behavior.

## Upgrade notes

- Install both binaries from this release. The host and endpoint now exchange
  environment-update messages and an initial publication acknowledgement.
- Stop the old host-side dworm process and run `dworm up` to inject the matching
  endpoint and publish the initial environment. Reopen existing shells to enable
  the new Bash initialization hook.
- Both configuration files are optional; existing projects need no new files.
- Refreshes run only while the original `dworm up` process remains alive,
  including its foreground `--daemon` mode.
- Already-running applications retain their inherited environment. Plain
  `docker exec` and container startup services do not load dworm's snapshot;
  use `dworm shell` or `dworm exec` for environment-aware launches.
