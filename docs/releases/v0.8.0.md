# v0.8.0 — One background instance per workspace, shared by all commands

## Highlights

The bridge to a devcontainer (port forwarding, agent and credential forwarding,
the exec socket) now lives in a long-lived **instance** per workspace, like
`tmux new -A` or SSH ControlMaster. Every dworm command is a client: it makes
sure the instance runs, starting it in the background if needed, and then talks
to it over the unix socket. Closing a shell no longer tears down the bridge for
everyone else, a broken bridge heals itself, and interactive sessions run on a
PTY inside the container, so killed clients leave no processes behind.

## Changed CLI behaviour

- **`dworm up`** ensures the instance runs (starting it detached if needed). On a
  terminal it then opens the shell; **leaving the shell leaves the instance
  running**. Use `dworm stop` (instance only) or `dworm down` (instance and
  container) to end it. Without a terminal, `dworm up` waits until the instance
  is ready, prints a one-line summary, and exits 0.
- **A second `dworm up` no longer fails** with exit code 3: it attaches to the
  running instance. Only `dworm up --foreground` exits 3 when an instance runs.
- **`dworm up --daemon` is deprecated**; use `dworm up --foreground` (same
  behaviour: the instance runs in the foreground, e.g. under systemd).
- **`dworm exec` and `dworm shell` start what is missing**: the instance and, when
  the container is stopped, the container (`devcontainer up`). `--no-start` makes
  them fail instead.
- **`dworm exec` no longer falls back to `docker exec` silently.** It always runs
  over the instance, with or without a terminal. `--no-bridge` explicitly uses
  plain `docker exec` (no forwarding, no process cleanup).
- **`dworm shell` opens the TUI with the status bar** (forwarded ports, instance
  state, logs), like `dworm up` on a terminal.
- **`-e` on `dworm up`/`dworm shell` only applies when they start the instance.**
  If an instance already runs with other values, dworm prints a warning naming
  `dworm stop`. `dworm exec -e` still applies per command.
- **`dworm down`, `dworm remove`, and `dworm rebuild` stop the instance first.**
- **A broken bridge no longer ends the instance** (see below). Under systemd,
  `dworm up --foreground` exits non-zero only on unrecoverable errors.
- Subcommands accept `-v/--verbose` (startup progress); `dworm -v` still prints
  the version.

## Added

- **`dworm stop`** stops the instance and leaves the container running.
- **`dworm up -d/--detach`** only ensures the instance runs and is ready.
- **`dworm logs [-f] [--json] [-n N]`** shows the instance's recent log lines;
  `-f` follows its events (starting the instance if needed), `--json` prints the
  raw event stream.
- **Startup progress:** while `devcontainer up` builds or starts the container,
  clients show its output on a terminal (or with `-v`). `--timeout` (default 15
  minutes) bounds the wait.
- **Self-healing bridge.** When the endpoint, its `docker exec`, or the container
  goes away, the instance reconnects: it re-injects the endpoint and re-sends the
  environment and forwarding configuration. While the container is down it
  retries for two minutes (covering `docker restart`), then stops. Meanwhile host
  port listeners stay open but refuse connections; running processes are lost
  (framed clients get exit code 255 with `"error":"bridge lost"`, raw clients a
  closed connection). The TUI shows `reconnecting...` and starts a new shell once
  the instance is ready again.
- **Interactive sessions on a PTY in the container.** `dworm shell`, the TUI, and
  `dworm exec` on a terminal run over the instance with a PTY allocated by the
  endpoint (window size changes are forwarded). When the client disconnects, the
  session is hung up like a closed terminal: SIGHUP, then SIGTERM, then SIGKILL
  after 5 seconds, for every process of the session.
- **Socket ops.** The first request line on the socket takes an `op`: `exec` (the
  default, so v0.7.0 clients keep working; now with optional `tty`), `events`
  (state, ports, log, exec_started, exec_exited, client events, with a snapshot of
  recent history; slow subscribers get `dropped` markers instead of blocking the
  instance), `status` (live state), and `stop`. Before the instance is ready, exec
  requests get `{"ok":false,"error":"not ready","code":"not_ready"}`.
- **`dworm status --json`** reports `up.state`, `reason`, `mode`
  (`detached`/`foreground`), `reconnects`, `clients`, `log_path`, and the
  instance's `dworm_version`, live from the instance. The v0.7.0 fields are
  unchanged.
- **Endpoint logs over the bridge.** Endpoint messages travel over the control
  channel (bridge protocol version 3) and appear as `log` events with
  `source: endpoint`. Detached instances log to `<runtime dir>/<hash>.log`
  (5 MiB, rotated once to `.log.1`).

## Upgrading

Install the new host (`dworm self-update`), stop any running v0.7.0 `dworm up`
(Ctrl-C, or `dworm stop`, which sends it SIGTERM), and run any dworm command.
Clients refuse to talk to an instance of another dworm version ("instance runs
vX, this is vY; run `dworm stop`"), so after later upgrades run `dworm stop`
once per workspace.

Unattended setups can drop per-project systemd units and the exit-code-3 special
case: `dworm up -d` returns 0 whether it started the instance or found it
running. Units that keep running the instance should use `--foreground` instead
of `--daemon`.

## Known limitations

- `dworm exec --no-bridge` uses `docker exec` and can leave processes behind when
  the client is killed.
- Running processes do not survive a bridge reconnect, and there is no way to
  reattach to a running exec or replay its output.
- Raw-mode clients that half-close and then disconnect are detected via
  `POLLHUP`, which is Linux-only. Framed mode is unaffected.
