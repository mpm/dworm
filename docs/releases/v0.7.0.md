# v0.7.0 — Unattended use: daemons, status, and exec over the bridge

## Highlights

dworm can now be driven by other programs and supervisors: `dworm up --daemon`
behaves well under systemd, `dworm status --json` reports machine-readable state,
and processes can be run through a running `dworm up` over a local unix socket,
with reliable cleanup when the caller goes away.

## Added

- **`dworm exec` stdio passthrough.** stdin is always forwarded; a TTY is
  allocated only when stdin and stdout are both terminals, so
  `printf 'a\nb\n' | dworm exec -- cat` prints exactly `a\nb\n`. stdout carries
  only the command's output, stdin EOF reaches the command, and the command's
  exit status becomes dworm's.
- **`dworm exec --workdir/-w <path>`** selects the working directory inside the
  container.
- **Single `dworm up` per workspace.** An `flock` in `$XDG_RUNTIME_DIR/dworm/`
  (fallback `/tmp/dworm-$UID/`) guards each workspace. A second `dworm up` exits
  immediately with **exit code 3**; use `dworm shell`/`dworm exec` alongside it.
- **State file** (`<hash>.json` next to the lock) with PID, container, remote
  user, workspace folder, start time, connection state, forwarded ports, and the
  exec socket path.
- **`dworm status --json`**, and a richer human-readable `dworm status`:
  container (also when stopped), remote user, workspace folder, whether a
  `dworm up` is running, its forwarded ports and exec socket. See `AGENTS.md` for
  the field reference.
- **Exec socket.** Every `dworm up` listens on `<hash>.sock` (mode 0600, same
  user only on Linux). One JSON request line starts a process in the container
  with the published dworm environment; `raw` mode then turns the connection into
  a plain stdin/stdout byte stream (half-close = stdin EOF), `framed` mode carries
  stdout, stderr, signals, and the exit status. Processes run in their own
  process group, which receives SIGTERM and, after 5 seconds, SIGKILL when the
  caller disconnects early or the bridge ends. Up to 32 concurrent processes.
- Without a terminal, `dworm exec` uses that socket when a `dworm up` is running,
  so even a SIGKILLed `dworm exec` leaves no process behind.

## Changed

- **`dworm exec` and `dworm shell` start in the workspace folder** (the
  in-container path of the project directory) instead of the image's working
  directory (`/` for most images). Use `dworm exec -w /` for the old behavior.
- **A second `dworm up` for the same workspace now fails** (exit code 3). Before,
  both ran: the second started another endpoint that replaced the first one's
  SSH/GPG/git-credential sockets and environment snapshot, forwarded already
  taken ports on random local ports, and removed the shared sockets when either
  exited, which broke forwarding for the other.
- **`dworm up --daemon` under systemd:** SIGTERM/SIGINT exit 0 and leave the
  container running, also when the signal reaches the whole cgroup; a broken
  bridge (endpoint dies, container stops or restarts) exits non-zero so
  `Restart=on-failure` reconnects. See the README for a unit file.
- **Logs** use plain `\n` line endings when stderr is not a terminal (journald,
  files); carriage returns are only added on terminals.
- `dworm status` exits 0 when the workspace has no container.
- Bridge protocol version 2: host-opened streams start with a stream type
  marker. Host and endpoint are always from the same build (the endpoint is
  embedded and injected on every `dworm up`); a mismatch now fails at startup.

## Upgrading

Install the new host (`dworm self-update`), stop any running `dworm up`, and
start it again to inject the matching endpoint. Exec socket state appears in
`dworm status --json` once the new `dworm up` is running.

## Known limitations

- Interactive TTY sessions (`dworm exec -- bash` in a terminal, `dworm shell`)
  still use `docker exec -it`; a killed client can leave their processes running.
- Raw-mode clients that half-close and then disconnect are detected via
  `POLLHUP`, which is Linux-only. Framed mode is unaffected.
