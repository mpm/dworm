# v0.8.1 — Compose-aware `dworm remove`, `dworm exec` across reconnects

## Fixed

- **`dworm remove` removes the whole Compose project** of a Compose-based
  devcontainer (`dockerComposeFile`), found by its `com.docker.compose.project`
  label: all its containers (every service, running or stopped), the
  devcontainer's image, the images built for the project (e.g.
  `<project>-app:latest`), and its networks (e.g. `<project>_default`).
  Previously only the devcontainer and its `-uid` image were removed. Pulled
  images of other services are kept. The confirmation prompt lists what will be
  removed, and dworm reports what it removed. Single-container devcontainers
  are removed as before. ([#1](https://github.com/mpm/dworm/issues/1))
- **`dworm exec` no longer fails right after a container restart.** When the
  instance is reconnecting, `dworm exec` waits (bounded by `--timeout`, default
  15 minutes) until it is ready again and then runs the command, instead of
  exiting 1 with `not ready`. A command that was already started is never sent
  twice. ([#2](https://github.com/mpm/dworm/issues/2))
- **`dworm status` reports `reconnecting` as soon as the bridge is lost.** It
  used to report `ready` for about half a second while exec requests were
  already refused with `not_ready`. ([#2](https://github.com/mpm/dworm/issues/2))

## Added

- **`dworm remove --volumes`** also removes the Compose project's volumes (and
  the containers' anonymous volumes). Without it, volumes are kept, since they
  may hold data.

## Changed

- **`dworm exec` exit codes** separate dworm's failures from the command's:
  - **125**: dworm failed and the command was not run (usage error, the instance
    could not be started or did not become ready within `--timeout`,
    `--no-start` with a stopped container, a rejected request). Safe to retry.
    Previously these exited 1.
  - **126/127**: the command could not be executed or was not found (unchanged).
  - **255**: the command was started but dworm lost it (bridge lost, as before,
    and now also a lost socket connection, which used to exit 1). Its outcome is
    unknown.
  - Any other code is the command's own exit status.

  Other commands keep exit 1 for errors (and 3 for `up --foreground` when an
  instance already runs).

## Upgrading

Install the new host (`dworm self-update`) and run `dworm stop` once per
workspace with a running v0.8.0 instance; clients refuse to talk to an instance
of another version. The bridge protocol is unchanged.

Callers that matched `not ready` on stderr to retry `dworm exec` can drop that;
callers that treat exit 1 from `dworm exec` as a dworm failure should check for
125 instead.
